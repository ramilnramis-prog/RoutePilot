Run history

Run history (read-only)

Read-only history, oldest first, from GET /api/plans/{id}/runs. A run is never edited, reordered or deleted: only POST /api/plans/{id}/optimize (the Recalculate control) appends one row, and this view never writes history. The recorded recommendation of a run is the audit of what that run showed - it is history, never the plan's current first-stop decision, and it is never rewritten here.

Driver override controls (the driver decides)

Every control here changes server state through one documented endpoint and then re-reads the affected panels from the server. Nothing on this page applies a recommendation by itself: the accept control only ever sends mode=recommend with the stop the engine recommended and this page displayed (D4/D32/D39(d)).

First-stop decision

“Accept the recommendation” (the primary button in the Optimization card) sends POST /api/plans/{id}/selection with {"mode": "recommend", "stop_id": <the recommended stop>} and is refused unless that stop really is the engine's current recommendation. It is disabled until a recommendation has been read.

The manual picker lists only the stops the API reports as enabled. “Choose this stop instead” (labelled “Use this stop” in the override documentation) sends POST /api/plans/{id}/selection with {"mode": "manual", "stop_id": <the chosen stop>}: the choice is the driver's, its provenance is manual_choice and it is pinned (D5/D6/D7).

“Cancel the selection” sends DELETE /api/plans/{id}/selection and the plan returns to awaiting_first_stop_choice - the domain never substitutes a stop (D8/D9).

Recalculate

POST /api/plans/{id}/optimize recomputes the recommendation, computes the committed route and appends exactly one immutable run row. Afterwards the route, the selection state and the run history are all re-read from the server; the measured computation_seconds of the recalculation is shown.

Stops: disable / restore / priority

Each stop row offers its own edit controls. Both send PUT /api/plans/{id} with a stops list carrying exactly one change: {"stops": [{"stop_id": …, "enabled": false|true}]} to disable or restore, and {"stops": [{"stop_id": …, "priority": <the new priority>}]} to change the priority. There is deliberately no drag/reorder control (out of scope, D21/D39(d)).

Demo limitations / technical details
Latency: the exhaustive first-stop recommendation is computed synchronously and has no background job queue. The accepted MVP worst case at the ~50-enabled-stop portfolio scale is about 8 seconds; every computation reports its measured computation_seconds.

Data provenance (printed from the API's own report)

The API's own data-provenance warning and the source of the time zone data in use are printed here verbatim from GET /api/health once the capability report has been read.

How this workspace talks to the API

Opening a plan reads it through GET /api/plans/{id}. “Create / open the DEMO plan” calls POST /api/plans, which returns the same deterministic fixture every time instead of duplicating it. The controls change server state through the documented endpoints (GET /api/plans/{id}/recommendation, POST /api/plans/{id}/selection, DELETE /api/plans/{id}/selection, PUT /api/plans/{id}, POST /api/plans/{id}/optimize) and then re-read the affected panels from the server. Why a request is read-only matters here: GET /api/plans/{id}/route, GET /api/plans/{id}/runs and GET /api/runs/{run_id} compute or read and write nothing, so reading a route or a stored run can never append a run row or change the driver's decision.

Engine and state machine

The first-stop recommendation is a live, exhaustive evaluation of every enabled stop as the first service stop: each candidate is a complete route (including the FINISH leg), and a candidate whose complete route misses a hard service window is rejected rather than ranked (v2 section 14). The plan's own first-stop state machine moves between awaiting_first_stop_choice and first_stop_selected; a selection is pinned once made, and cancelling clears it. A stored run records the recommendation that execution produced: that is an audit of history, never the plan's current decision.

What this build does NOT do

Read from the API's own capability report (GET /api/health, not_implemented_capabilities, route_modes and timezone_data) - not from a list written in this page. An unimplemented capability is never presented as working (D16).

Synthetic data and geometry

The data is DEMO / SYNTHETIC: not real addresses, not real opening hours, not real routing, no traffic. The line on the map is synthetic straight-line geometry joining the returned route order - it is not road routing, carries no road distance and answers no turn-by-turn or geocoding request. Travel time and distance come from the DEMO/SYNTHETIC provider, never from a real RoutingProvider.

RoutePilot recommends, the driver decides. Synthetic demo data is never presented as real routing, traffic or opening hours (spec sections 33/34; D15/D16/D23/D32).
